# Summary

Four independent auditors reviewed the codebase against ISO/IEC 25010:2023 §3.5 (faultlessness, availability, fault tolerance, recoverability). All four found the sync/link/error-handling paths unusually well hardened — bounded Plaid/fetch timeouts, a cross-process advisory lock with re-read-under-lock semantics, single-flight coordination, pool idle-error logging, page/retry budgets, and the bounded cursor hold, all matching their design records. Two previously-found majors were verified fixed: Plaid Link update-mode repair now exists (`createLinkToken(accessToken?)`, `createRepairLinkToken`, `connection-repair-update-mode`), and pool idle-client errors are logged instead of crashing (`db-pool-errors-logged`). The one finding reached by **all four auditors** (two rating it major) is that the "every network wait is bounded" principle (`requests-have-deadlines`) was never extended to Postgres.

# Major Concerns

- **No timeout on Postgres connection acquisition or query execution** (`src/lib/db.ts:22-26`; also `scripts/seed-cards.ts:208-210`) — flagged by all 4 auditors (2 major, 2 moderate). The pool is constructed with only `connectionString`: no `connectionTimeoutMillis`, `statement_timeout`, or `query_timeout`, and no call site sets one. This is the one network dependency the repo's own `requests-have-deadlines` principle was never extended to (Plaid has a 60s axios timeout, client fetches abort at 120s). A stalled TCP flow, replica failover, or long-blocked lock hangs a request indefinitely with no log line; `withItemSyncLock`'s `pool.connect()` (`src/lib/sync-lock.ts:13`) compounds this by holding a dedicated connection across all Plaid I/O, so hangs both wedge the per-item sync lock/single-flight guards and can exhaust the default 10-connection pool — the exact "transient fault becomes a permanent, invisible outage" failure mode the project already fixed for Plaid and the pool's idle-error case. Recovery requires a manual process restart.

# Moderate Concerns

- **No React error boundary anywhere in the App Router** — flagged by 3 auditors. No `error.tsx`/`global-error.tsx` exists under `src/app` (confirmed by search); `src/app/layout.tsx` is a bare shell. Fetch-level failures are deliberately contained (`useLoadProtocol`, `ErrorNotice`, the `partial-load-rendering` family), but an uncaught render-time exception in any client component blanks the whole route to Next's default error UI with no retry affordance — the one hole in an otherwise careful fault-containment strategy.
- **Row locks taken during sync have no `lock_timeout`** (`src/lib/sync-outcome.ts:43-47` and `src/lib/sync-carry.ts:41-50`, both `.for('update')` inside `runSyncItem`'s transaction, `src/lib/sync.ts:75-97`) — flagged by 2 auditors. `src/lib/categories.ts:84` explicitly caps its own equivalent lock wait at 3s, so the codebase is internally inconsistent: one write path treats an unbounded lock wait as unacceptable, the other doesn't. A blocked lock hangs the whole sync transaction (same silent-hang class as the major above).
- **No incremental checkpointing across a `transactionsSync` page drain** (`src/lib/plaid.ts:239-273`, `src/lib/sync.ts:71-97`) — flagged by 2 auditors. Up to 200 pages accumulate in memory and the cursor is persisted once, after the entire drain; a mid-drain failure (network drop, Plaid 5xx on page 150) discards everything fetched and retry restarts from the same cursor with no forward-progress guarantee. Low impact under the documented small-initial-sync assumption, but a recoverability gap for a large backlog over flaky connectivity.
- **No permanent-vs-transient distinction or backoff for sync failures** — flagged by 2 auditors. `syncTransactions` (`src/lib/plaid.ts:255-266`) retries only the empty-cursor "not ready" case; any other transient error (one-off 5xx) fails the item's whole attempt the same way a permanent `ITEM_LOGIN_REQUIRED` does. The hourly scheduler (`src/lib/sync-scheduler.ts`) retries everything indefinitely with no backoff, and a manual "Sync all" surfaces a hard failure for a one-off blip.
- **`DELETE /api/items/[itemId]` does not take the per-item sync lock** (`src/app/api/items/[itemId]/route.ts`) — `withItemSyncLock` is the sole mutual-exclusion mechanism for an item's sync state and is used only from `syncItem`. A delete racing a concurrent sync removes rows out from under it; the sync's transaction then rolls back on an FK violation or the "item row disappeared mid-sync" throw — no corruption, but it surfaces as a confusing uncategorized 500 rather than a clean allow-listed outcome. Worth locking, or documenting why unlocked is acceptable (as `cross-process-sync-lock` does for sync-vs-sync).

# Minor Concerns

- **Item deletion can orphan a local row on partial failure** (`src/app/api/items/[itemId]/route.ts:31-39`) — flagged by 2 auditors: Plaid `removeItem` succeeds, then the local delete fails, leaving a row pointing at an invalidated token. One auditor verified this self-heals on retry (the second attempt's `ITEM_NOT_FOUND` is treated as success), so impact is low.
- **`items.error` is a single field, so concurrent failure modes mask each other** (`src/lib/sync-outcome.ts:56-62`) — flagged by 2 auditors: the skipped-rows message and `ACCOUNT_REFRESH_FAILED_MESSAGE` are mutually exclusive in one column; if both occur in one cycle, one is silently dropped.
- **No process-level `unhandledRejection`/`uncaughtException` backstop** — promise discipline is lint-enforced (`promise-discipline-linted`) and observed fire-and-forget sites are internally caught, but a rejection escaping from dependency internals can crash the process and silently take the in-process hourly scheduler with it. A last-resort `process.on('unhandledRejection', ...)` log is a cheap backstop.
- **`linkItem`'s parallel enrichment surfaces a bare error on durable partial success** (`src/lib/link.ts:151-160`) — `getItem`/`getAccounts` failures propagate even though `storeItemShell` has already persisted the access token; the surfaced error doesn't reflect the partial success on disk.
- **Sequential per-item sync has no per-item wall-clock budget** (`src/lib/sync-all.ts:25-37`) — one hanging institution delays every other item that cycle (compounded by the missing DB timeouts).
- **`listTransactions` page and count are two non-atomic reads** (`src/lib/transactions.ts:24-43`) — a concurrent sync between the two queries can yield a `total` inconsistent with the returned page, confusing the last-page clamping in `useTransactionPage.ts:40-41`. Low impact for a single-user app polling every 60s.

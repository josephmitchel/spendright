# Summary

Four independent auditors reviewed the codebase against ISO/IEC 25010:2023 §3.9. All four converged on the same scoping: SpendRight is a single-user, local, read-only-to-Plaid tool that moves no funds, so the relevant harm class is **property** — whether the app can mislead the user into a bad financial decision by presenting incorrect, stale, or unqualified figures as trustworthy, or perform an irreversible destructive action without adequate warning (Safe Integration is not applicable). All verified substantial deliberate safety machinery already in place: bounded cursor-hold with progressive escalation before an explicit logged drop, per-account/per-item failure isolation, fail-closed config validation, accurate cascade wording in the removal `confirm()`, Plaid-revoke-before-delete ordering, historical reward-rate snapshots, the spend/inflow sign check constraint, `numeric` (not float) money columns, and stale-list edit disabling. **No major findings.** Three auditors independently confirmed the same four moderate gaps, which also match the prior same-day audit run — the code is unchanged, so these are recurring findings.

# Major Concerns

None. No path was found by which the app could directly cause loss of funds; destructive paths are bounded and warned.

# Moderate Concerns

- **Account detail page shows balances with no path to the staleness/error warning that exists on the home page** — flagged by 3 auditors. `AccountIdentity` (`src/app/accounts/[accountId]/page.tsx:44-60`) renders `balanceCurrent`/`balanceAvailable`/`balanceLimit` unconditionally; a failed refresh writes `ACCOUNT_REFRESH_FAILED_MESSAGE` to `items.error` (`src/lib/sync-outcome.ts:29-32`), but `GET /api/accounts/[accountId]` never joins `items` and `useAccountData.ts:20-43` never fetches item state — the warning renders only on the home page (`page.tsx:92-98`). The exact screen a user checks before a spending decision cannot show the one hazard warning the system already computed.
- **Scheduled background sync can fail as a whole run with zero user-visible signal, repeatedly** — flagged by 3 auditors. `sync-all.ts:22` selects all items _before_ the per-item try/catch; a failure there (DB down, pool exhausted) throws out of `runSyncAll` before any `items.error` is written, and `sync-scheduler.ts:25-27` catches it with only `logError`. This can recur silently every hourly tick while the UI shows old balances with no banner — precisely the "syncs fail silently" mode `scheduled-sync.md` was written to avoid. The manual path (`useSyncAll` → `ErrorNotice`) fully surfaces the identical failure, so the two paths to the same operation have inconsistent fail-safe postures.
- **No "as of" timestamp anywhere in the UI for balance data** — flagged by all 4 auditors (one as minor). `accounts.updatedAt` is already selected into the served row (`src/lib/accounts.ts`) but no client code renders it. Combined with the two findings above (the active warning paths can themselves fail), there is no passive, always-available freshness cue independent of the failure-detection machinery working correctly.
- **Flat reward-rate model asserts rates as fact past real-world caps** — flagged by 3 auditors. `cardCategories.rate` has no cap/threshold concept (`src/db/schema.ts:39-40`); the seeded Amex Blue Cash Preferred's 6% categories really cap at ~$6,000/year then drop to 1%. The flat rate is written per transaction and rendered unconditionally (`TransactionTable.tsx`, `rateCellText`), so past the cap the app keeps asserting a materially too-generous rate indefinitely — an operational-constraint gap in the app's core decision-guidance function. (Also raised under Functional Suitability.)
- **Seeded reward-rate values are unbounded and unverified** — one auditor, framing the seed-validation gap as a safety constraint: `assertSeedIsValid` checks structure (slugs, matchers, uniqueness) but not that `rate` is plausible/non-negative, so a transposition typo (`60` for `6`) ships silently as authoritative guidance. Relatedly, the repo's `Verified-on:` mechanism re-checks package claims but nothing analogous flags that seeded rates are hand-asserted and unverified against the issuer's actual current terms, which change periodically.

# Minor Concerns

- **Warnings direct the user to remediation they can't perform** — `ACCOUNT_REFRESH_FAILED_MESSAGE` and the skipped-sync messages (`sync-messages.ts`) say "check the server log"; no in-app action is offered alongside (the `RepairConnectionButton` covers only a subset of Plaid error shapes).
- **All error severities render with identical visual weight** (`ErrorNotice.tsx`) — a transient blip, a recoverable skip, an irreversible post-`MAX_SKIPPED_SYNCS` cursor drop, and a systemic `BAD_CONFIG` failure all render as the same undifferentiated paragraph, giving no cue which warnings need action now.
- **`scripts/seed-cards.ts` reconcile is destructive-by-default** — no confirmation, dry-run, or target-environment echo; a misdirected `DATABASE_URL` or truncated seed file silently retires the live catalog. Bounded by retire-not-delete semantics (`categories-retired-not-deleted.md`), but unguarded at the point of the destructive run.
- **`matchCard` has no guard against a semantically wrong seed mapping** (`src/lib/cards.ts:8-18`) — a wrong or duplicated `plaidAccountNames` entry silently attaches an account's transactions and reward reporting to the wrong card; structural seed validation can't catch it.
- **`kindForAmount` routes `NaN` silently to `'card'`** (`category-kinds.ts:6-9`) — documented as intentional, but a malformed upstream amount is categorized and reward-rated as normal spend with no data-quality flag.
- **No duplicate-institution guard at link time** (`api/exchange/route.ts`) — re-linking creates a second independently-syncing item; double-counting is unlikely via Plaid-ID upserts but the condition is undetected and unwarned.
- **No positive freshness indicator on the success path** — hazard warning covers explicit failure but not staleness in the absence of failure (subsumed by the "as of" timestamp concern above; listed by one auditor as the asymmetry itself).

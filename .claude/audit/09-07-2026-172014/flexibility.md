# Summary

Four independent auditors reviewed the codebase against ISO/IEC 25010:2023 §3.8 (adaptability, scalability, installability, replaceability), excluding settled design decisions (single-card catalog, code-only catalog mechanism, localhost/no-auth posture, migrations-only Postgres, exact-name matching as a mechanism). Noted strengths: the provider-adapter boundary (`provider-types.ts`) cleanly separates Plaid shapes from app-owned shapes, the `PLAID_ENV`/`PLAID_PRODUCTS`/`PLAID_COUNTRY_CODES` surface is env-driven and fail-fast validated, and compiler-enforced category-kind exhaustiveness aids adaptability. **No agreed major finding.** One auditor rated the in-memory concurrency primitives a major scaling ceiling, but another auditor directly verified that the cross-process Postgres advisory lock (`src/lib/sync-lock.ts`, added per `cross-process-sync-lock.md`) has since closed the cursor-race portion of that concern — the residual (in-memory single-flight/dedupe guards, no horizontal-scale story) is reported as moderate below with the disagreement noted.

# Major Concerns

None agreed. (See the first moderate concern for the one contested major.)

# Moderate Concerns

- **Horizontal scaling remains unaddressed beyond the per-item advisory lock** (`src/lib/global-singleton.ts`, `src/lib/async-coordination.ts` `serializeByKey`/`singleFlight`, consumed by `sync-all.ts:13-19` and `sync.ts`) — one auditor rated this major on the theory that all concurrency guarantees are `globalThis`-scoped; another verified the Postgres advisory lock now serializes same-item syncs cross-process, closing the cursor-write race. What genuinely remains process-local: the sync-all single-flight guard and scheduler singleton (multiple replicas would each run their own hourly scheduler and could run overlapping sync-alls, safe per-item but duplicative), and no design record states the single-process assumption as a boundary condition.
- **No user/tenant scoping anywhere in the data model** (`src/db/schema.ts`) — flagged by 2 auditors. No table carries a `user_id`; the only "user" in the codebase is the hardcoded `client_user_id: 'spendright-user'` (`src/lib/plaid.ts:119`). `single-user-localhost-no-auth.md` records the missing auth as a future blocker but not this deeper commitment: multi-user support is a migration touching every table's unique constraints and every query in `src/lib/*`, not "add auth." Worth recording as a distinct adaptability cost.
- **No key-rotation/versioning path for `ENCRYPTION_KEY`** (`src/lib/crypto.ts:10-55`) — flagged by 3 auditors. Ciphertext (`iv:tag:ciphertext`) carries no key ID and `decrypt` has no previous-key fallback, so a routine key rotation permanently invalidates every stored Plaid token; the blast radius grows with every linked institution and no design record tracks a mitigation path. (Also raised under Security.)
- **Reward-type is a closed two-value enum duplicated across three unlinked sites** — flagged by 2 auditors. `'cashback' | 'points'` is independently encoded in `src/db/schema.ts:25`, `src/db/cards.seed.ts:8`, and the UI branch at `TransactionTable.tsx:92`, with no shared source of truth and no exhaustiveness tie (contrast `CategoryKind`'s `assertNeverKind`). A plausible near-term reward type (miles, tiered) requires a migration plus lockstep edits in three places.
- **Card-catalog drift has no operational recovery path** — flagged by 2 auditors. An institution-side product rename silently unmatches the account (`matchCard`, `src/lib/cards.ts:8-18`) and the only repair is editing `cards.seed.ts` and re-running `npm run seed:cards` — a source change and redeploy to recover from an environmental drift, with no runtime/config/UI path. Distinct from the settled catalog-size and name-matching decisions; this is about the adaptation _mechanism_ being code-only.
- **Build/dev/start pipeline hard-depends on POSIX `chmod` — blocks Windows entirely** (`scripts/tighten-next.mjs:14`, invoked from `predev`/`prebuild`/`postbuild`/`start.mjs`) — flagged by 3 auditors (one moderate, two minor/cross-referenced). Fail-closed by design (`build-cache-secret-permissions`), so on Windows with no `chmod` on PATH the entire toolchain refuses to run; no `fs.chmod` fallback and no documented Windows position. An installability gap the design record doesn't accept as a tradeoff. (Also raised under Compatibility.)
- **Strictly sequential `syncAllItems`** (`src/lib/sync-all.ts:25-37`) — cross-item serialization has no correctness rationale (per-item locks already isolate races); sync wall-time grows linearly with linked institutions. Covered in depth under Performance Efficiency; restated here as the scalability face of the same issue.

# Minor Concerns

- **Plaid Link language hardcoded to `'en'`** (`src/lib/plaid.ts:122`) — flagged by 3 auditors. Sibling parameters in the same request are env-driven via `getEnvEnumList`; a `PLAID_LANGUAGE` knob following the same pattern would restore consistency and support non-English locales.
- **Sync/poll cadences and Plaid tuning knobs are fixed constants** — flagged by 3 auditors. `STARTUP_DELAY_MS`/`INTERVAL_MS` (`sync-scheduler.ts:9-10`), the 60s poll default (`useVisiblePoll.ts:6`), and `PLAID_TIMEOUT_MS`/`NOT_READY_DELAY_MS`/`SYNC_PAGE_SIZE`/`MAX_SYNC_PAGES` (`plaid.ts`) have no env override; adapting to different network/workload conditions requires code changes.
- **`pg.Pool` sizing is not environment-driven** (`src/lib/db.ts:22-26`) — flagged by 3 auditors; also `PAGE_SIZE`/`MAX_PAGE_LIMIT` (`pagination.ts`) are hardcoded. Cheap to add now, disruptive to retrofit.
- **No provider-neutral seam for the linking flow** (`src/app/PlaidLinkButton.tsx`, `src/lib/api-paths.ts`) — flagged by 2 auditors. Data DTOs are cleanly adapted, but the connect UI and API route surface remain Plaid-shaped end to end; a second aggregator means rebuilding the connect flow, not just an adapter. Low severity — aggregator widgets are bespoke regardless.
- **Cross-process locking is Postgres-specific** (`sync-lock.ts`, `pg_advisory_lock`/`hashtextextended`) — deliberate and documented, but swapping the persistence engine would require redesigning concurrency control; noted under replaceability.
- **No end-user override for account-to-card matching** — a never-matching account stays "Card not supported" with no manual assignment fallback; a documented current-stage gap (`supported-account-rule.md`), noted for completeness.
- **Architecture is hardwired to the localhost context of use** (`src/proxy.ts` `LOCAL_HOSTNAMES`, no auth anywhere) — deliberate and README-documented as a pre-deployment blocker; named here because adapting beyond "one browser on the same machine" requires foundational changes to `proxy.ts`, `env.ts`, and every route, not a config toggle.

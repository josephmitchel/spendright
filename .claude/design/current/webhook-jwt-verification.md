The webhook route is the one route that must be internet-reachable (through a tunnel), so unlike the rest of the app ([[single-user-localhost-no-auth]]) it cannot rely on localhost being the only caller. The `Plaid-Verification` JWT is verified with Node's crypto, no new dependency: alg pinned to ES256 (never read from the header), the key fetched from Plaid by kid and cached per kid with an hour TTL (so a Plaid-side expiry takes effect without a restart), keys Plaid marks expired refused, the signature checked (ieee-p1363), `iat` within five minutes, and `request_body_sha256` compared timing-safe against the hash of the raw body bytes. A bogus kid is a 401, not a 502, and a segment that decodes to JSON but not to a plain object (`null`, a number, an array) is refused before any claim is read off it — the 2026-09-04 audit found `base64url("null")` as the header segment threw past `reject()` and turned the uniform 401 into a 500. Every failure logs its specific reason server-side (the attacker-controlled kid JSON-stringified, so a newline in it cannot forge a log line) and answers the same generic 401 `UNVERIFIED`.

An anonymous caller also cannot make the route spend resources on their behalf:

- **Body work is prechecked.** A request with no `Plaid-Verification` header or a declared Content-Length above 64KB (Plaid webhooks are a few KB) is 401'd by `precheckPlaidWebhook` before the body is decoded or hashed. The precheck cannot run before the body is *buffered*: with `src/proxy.ts` present, Next buffers every request body before the proxy or any route code runs, so the actual bound on buffering is the 128KB `proxyClientMaxBodySize` cap in `next.config.ts` — a truncated oversized body then fails verification closed via the hash mismatch. (The 2026-09-04 audit corrected this record's earlier claim that the precheck ran pre-buffering; what it saves is the decode and SHA-256. Slowloris-style connection holding on the tunnel remains possible at that layer and is a reverse-proxy concern, not an app-level one.)
- **Outbound key fetches are budgeted, not just cached — and the budget bounds Plaid calls, never verification.** Only Plaid's own "no such key" answer (a Plaid error body on a non-429 4xx) is negatively cached, for five minutes; a network failure, 5xx, or rate limit proves nothing about the kid and is not cached — the 2026-09-05 audit found the earlier cache-any-failure behavior pinned the *genuine* kid as nonexistent for five minutes after a transient blip. Negative caching alone cannot bound a spray of never-repeated kids (each is a cache miss by definition), so key fetches are capped at 10 per five-minute window — far above the legitimate rate of one fetch per Plaid key rotation. A TTL-stale key is kept as a fallback: when the budget is exhausted or a refresh fails transiently, verification proceeds with the stale key instead of 401ing (safe because `jwk.expired_at` is the authoritative expiry, checked on every use; the TTL is only a freshness convenience). This closes the 2026-09-05 finding that a sustained kid-spray (~11 requests per window, no valid signature needed) held the budget at its cap indefinitely, so once the genuine key's TTL lapsed every real webhook 401'd for the duration of the spray — this record's earlier "retried, not lost" argument held only for transient sprays. The kid cache is size-capped at 50 and, when full, evicts the stalest negative first, then the stalest TTL-expired key, and a fresh key only if every entry is one: under a spray the map fills with fresh negatives while the genuine key carries the oldest timestamp, so evicting purely by staleness would flush the genuine key first (found and fixed 2026-09-04), and a TTL-expired genuine key outranks every negative because it is the stale-fallback that keeps verification alive (2026-09-05). The map is never cleared wholesale.

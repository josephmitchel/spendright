A category pick writes into the row immediately so the controlled select never snaps back. Each row keeps a promise chain (`patchChain`, joined through the shared `serializeByKey` since 2026-09-06) so it has at most one PATCH in flight and issue, commit and response order agree. Because sends settle strictly in issue order, a pending counter is the whole bookkeeping (per row: pending count, pre-burst baseline row, newest committed server row — an explicit sequence number would be redundant with the chain): the counter hits zero exactly when the burst's newest patch settles, which is when the row reconciles — newest committed response, else the baseline — and when that patch's outcome (only) is surfaced. Failures are keyed per row like the rest of the bookkeeping and rendered inside the failing row's category cell (2026-09-06, confirmed by the user after a quality audit found the original single shared error slot let concurrent edits on different rows silently clear one another's failures — the select would snap back with no explanation); a row's error clears when that row's next pick starts or succeeds — or when the pager leaves the page it was raised on (2026-09-06, after a quality audit found a long-gone edit's failure resurfacing out of context on a later visit to that page). Reconciliation merges only the category columns into the current row, so a page re-fetch that landed mid-burst keeps its fresher non-category data — and since 2026-09-06 that limit is structural, not prose: `useCategoryPatches` no longer receives the raw list setter but `useTransactionPage`'s `applyCategoryPatch(transactionId, fields)`, typed to the category columns (`CategoryPatch`, derived from `categoryKindKeys`), so a writer outside the load protocol cannot replace rows or touch fields a concurrent re-fetch owns (`CategoryPatch` and `categoryFields` live in the shared `category-patch.ts` since 2026-09-07, so the two hooks depend on it one-way instead of on each other). The protection is two-directional (2026-09-07, user-confirmed after a quality audit found the silent poll's wholesale list replacement snapping the select back mid-burst): a row with an open burst is held, and a settling load merges a held row's on-screen category fields (`categoryFields`) over the fetched row instead of overwriting them. A hold outlives its burst by one successful load (`held` → `releasing` → released) because a poll whose response was read before the burst's PATCH committed can settle after the burst ends; merging the already-reconciled on-screen fields for that one extra load is a no-op in every non-racy case.

Consolidated 2026-09-07 (user-confirmed after a quality audit found the burst/hold state machine split across the two hooks with an implicit call-ordering contract — the holds were set from one hook and released inside the other's load callback): the whole per-row state machine now lives in one plain class, `CategoryWriteState` (`category-write-state.ts`), with one explicit state type per row (burst plus hold phase). `useCategoryPatches` drives it (`joinBurst`, `recordCommit`, `settleIfDone` — which closes the burst and returns the fields to reconcile); `useTransactionPage`'s load path uses only `fetchedRowMerger()` (a pure merger over a hold snapshot, safe inside the setState updater) then `releaseSettledHolds()`. The page owns the single instance and passes it to both hooks; the burst→hold transitions are internal to the class, so neither hook can order them wrongly. Works alongside [[no-category-clear]] and [[category-write-contract]]; responses go through [[single-response-reader]].

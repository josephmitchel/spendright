The security audit found the unauthenticated app reachable beyond the local browser two ways: the webhook tunnel (`ngrok http 3000` forwards the whole origin, not just `/api/webhook`) and the server's default `0.0.0.0` bind. Confirmed fix: the bind is the enforcement, and `src/proxy.ts` (Next 16's renamed middleware; runs on every request) is defense-in-depth on top of it.

- **The bind is what actually keeps the LAN out**: both `dev` and `start` run `-H 127.0.0.1`, so nothing off-host can open a socket at all. It must be unconditional, not dev-only, because the header checks below are forgeable on a direct TCP connection — Next fills `x-forwarded-*` with `??=` (only when absent), so a client-sent `Host: localhost` plus `X-Forwarded-For: 127.0.0.1` passes them, as the follow-up audit verified empirically against the running server.
- **The bind is asserted, not assumed** (2026-09-04 audit): the `-H` flag lives only in the npm scripts, and the Next CLI reads the hostname from nowhere else (no env or config fallback), so a bare `next dev`/`next start` binds every interface and silently discards the enforcement layer. `src/instrumentation.ts` therefore probes the server's own port on every non-loopback interface address shortly after startup (twice, since `register()` runs before listening) and exits the process if any accepts a connection.
- **Only header-injecting HTTP tunnels are supported** (2026-09-04 audit): the 404 layer holds against ngrok/cloudflared because they inject a non-loopback `Host` and the caller's real `X-Forwarded-For`. A raw TCP forward (`ssh -R`, socat, editor port forwarding) injects nothing, connects from loopback (so the bind does not apply), and hands the remote caller every header — it would expose the whole unauthenticated API. The README says to use only an HTTP tunnel; no in-code guard can distinguish a raw forward from the local browser.
- `/api/webhook` passes through untouched — it proves its caller cryptographically ([[webhook-jwt-verification]]). The exemption requires the normalized pathname and the raw request path to agree (2026-09-05 audit): Next normalizes `/_next/data/<anything>/api/webhook.json` to `/api/webhook` before the proxy runs but dispatches the literal path, so matching the normalized name alone would exempt a request the router treats as a different route — unreachable today (no catch-all route exists, so it 404s), but a live bypass the day a catch-all or rewrite is added.
- Every other path answers a uniform bodyless 404 unless the request is loopback end-to-end: Host is a loopback name (`localhost`, `127.0.0.1`, `[::1]`), `x-forwarded-host` (if any) is loopback, and every entry in the `x-forwarded-for` chain is a loopback IP. This layer holds only against callers that cannot forge cleanly — DNS rebinding (the browser sends the rebound Host) and forwarding tunnels/proxies that append the caller's real address to `x-forwarded-for` — which is exactly its job: keeping a tunnel from exposing every route. It is not a substitute for the bind. 404, not 403: a scanner learns nothing. A Host containing `/`, `\`, `@`, `?`, `#` or whitespace is refused before URL parsing (2026-09-05): `new URL()` would read `evil.com@localhost` or `localhost/evil` as a loopback hostname. No exploit existed (such a caller could as easily send `Host: localhost`, and the `x-forwarded-for` chain still names them), so this is parser hardening only. The unbracketed `::1` was dropped from the loopback set as dead code — `URL.hostname` only ever yields the bracketed form.
- CSRF: non-GET/HEAD/OPTIONS requests carrying an Origin get 403 unless it is same-origin with the request itself (http, exact host and port from the Host header) — browsers attach Origin to every cross-origin request, including preflight-free simple POSTs; Origin-less requests (curl) pass. Merely-local is not enough (2026-09-04 audit): any other locally-running site, e.g. a dev server on another port, is a different origin and must not be able to drive the API.
- Clickjacking (2026-09-04 audit): `next.config.ts` sends `Content-Security-Policy: frame-ancestors 'none'` (plus `X-Frame-Options: DENY`) on every path — a page iframing `http://localhost:3000` would produce same-origin clicks the Origin check cannot see.

- **Open (2026-09-05 audit): `next dev`'s `/__nextjs_*` endpoints bypass the proxy entirely.** The dev bundler's hot-reloader middleware runs before route resolution (`router-server.js` invokes it ahead of `resolveRoutes()`), so the "runs on every request" claim above does not hold for these paths in dev mode: with a tunnel up, an Origin-less caller (curl — exactly the tunnel threat model) reaches `/__nextjs_launch-editor`, `/__nextjs_attach-nodejs-inspector`, and the source-map/stack-frame endpoints past both this guard and Next's own `blockCrossSiteDEV` (which only checks Origin/Sec-Fetch headers, never Host). The proxy structurally cannot intercept them. They are dev-only — `next start` does not mount them — so the interim rule is: never tunnel to the dev server; run `npm run build && npm run start` whenever a tunnel is up. The confirmed direction (2026-09-05) is to retire the tunnel entirely in favor of a scheduler-driven sync, which removes the exposed origin altogether.

This is a guard for the tunnel and the LAN, not authentication — [[single-user-localhost-no-auth]] still blocks real deployment.
